# BlacKKing REA Workflow

Use the user's selected REA fork as the tool owner. A portable bundle supplies
core CLI/MCP and instructions, not authorization, account sessions, all analysis
engines, or evidence that a current client has discovered the server.

## Start from the actual request

Confirm the target, permitted operations, input version/hash, editable source
owner, required delivery and observable acceptance. Reuse existing files and
receipts by content identity instead of copying a complete case again. Keep
case material outside tool repositories. Ordinary source-only questions do not
require REA setup or project initialization.

Use an available `reverse-engineer-anything` skill and the registered REA CLI/MCP
schemas for format/backend routing. In a portable installation, resolve the
same bundle's runtime; do not replace it with `npx ...@latest`. Read
[target routing](references/target-routing.md) only for the selected format.
Missing optional engines reduce supported scope; they are not a reason to
install unrelated tools or change accounts.

## Build a scoped evidence chain

1. Preserve original inputs and inventory selected members. Maintain original
   paths, types, byte identities and extraction mappings.
2. Keep decompiled reading copies separate from original compiled bytes and
   editable reconstruction. Preserve warnings, failures and omissions.
3. Independently check critical original members and methods. Verify the
   producing command and genuinely new outputs before accepting re-encoding.
4. Label static checks, re-encoding, controlled original function execution,
   original application execution, reconstruction execution, browser execution
   and relocated package execution separately.
5. For browser acceptance, first hash the actual served critical payload and
   match it to the accepted build. Do not infer current version from a URL,
   listening port, old screenshot or source tree. Keep existing user services;
   record an isolated port separately from the default launch path.
6. Drive real controls for the selected scenario. Check confirmation completion,
   returns, failure/retry and applicable save/reload boundaries. Capture the
   actual state; a later screenshot may not show the earlier observed frame.
7. Verify distribution member hashes/CRC, selected-project closure, required
   runtime and licenses, then extract to an unrelated path with spaces and run
   through its own launcher/runtime. Keep completeness claims bounded.

Read [verification](references/verification.md) for the evidence fields,
independent review checklist and claim boundaries. Its receipt examples are
templates, not records of completed work.

## Independent review and close

When separate verification is available and useful, assign a reviewer who did
not author the change to inspect source/bytes, warnings, critical behavior and
the actual visible images. Record what the reviewer personally checked, what
was only operator-observed, and what remains unverified. Do not create extra
actors merely to satisfy a role name; follow current user authority and keep
writes isolated. A self-review is not an independent review.

Keep one authoritative editable case, a clear first-level local launcher when
requested, and independently usable distribution packages. Shortcuts may point
to that launcher. Never call recovered assets or representative playthroughs
proof of every commercial version, mode, character or platform.

Only remove exact generated work copies after keeper hashes, references and
ownership are checked. A tool/approval rejection means retain and report; do
not switch APIs, shells or paths to bypass it. Report completed scope, evidence,
residual limitations and the next practical action.

## Cost and decisions

Use the existing authorized environment and free tools. For a genuinely needed
non-paid choice within scope, state the recommendation, impact and question
time; continue independent work and use the recommended free reversible plan
after 15 minutes without an answer. Later answers steer work not yet done.
Timeout never authorizes paid operations, account or access changes, destructive
actions, scope expansion, or tool-required confirmation. Do not auto-purchase,
subscribe, recharge or enable a paid API. Read the current system proxy before
each shell network command; set/clear only command-local overrides.
